# 宪章问卷：用选择题引导立宪

立宪的 HIL 不是「给用户一篇草稿自己看着办」——那是把输入负担原样丢回给人。正确形态是**引导式问卷**：把宪章里必须由人拍板的维度变成选择题，用 AskUserQuestion 分批提问。用户的输入成本从「写一段需求文档」降到「点几下选择题」；全部选推荐项也能得到一部可开工的宪章。

## 出题分工

- **固定六维**（下表）必出，除非用户目标原话已经明确回答了某一维——那一维直接落定、宪章里标「（目标原话）」，不重复问。问已经答过的问题最伤问卷的信用。
- product-owner 调研后可以**追加自出题**：主流调研或 repo 现状暴露出的、答案会改变宪章内容的分叉。
- **只出「答案会改变宪章内容」的题**。能从 repo、目标原话或常识推出来的不问——问卷是减负工具，题目越多减负越少。每题必须写得出「这题的答案会改宪章哪一节」，写不出就删。

## 固定六维

| # | 维度 | 题型 | 选项来源与要点 |
|---|---|---|---|
| 1 | 目标用户 | 单选 | PO 从目标原话+主流调研给 2-4 个画像，推荐一个。画像写进宪章 U 条款，acceptance 每轮从这个视角验收 |
| 2 | 形态与平台 | 单选 | CLI / Web / 桌面 / 库…，按调研和 repo 现状推荐。落 F 条款 |
| 3 | 功能范围 | **多选** | 主流同类产品的功能清单（PO 调研产出），勾选的入「核心场景」G 条款，**没勾的自动进「非目标」N 条款**——这是防功能爆炸的主闸，所以清单必须把主流项列全：漏列的功能日后既不在目标里也不在非目标里，就成了发散的入口 |
| 4 | 质量档位 | 单选 | 测试严格度：每个新增行为带测试（推荐）/ 只覆盖核心路径 / 不引入测试。落 Q 条款 |
| 5 | 预算与停机 | 单选 | 「迭代上限 × 每轮功能数」的组合档，如 5 轮×3 个（推荐）/ 3×2 快速验证 / 8×3 充分打磨。落 B 条款 |
| 6 | 授权边界 | **多选** | 本地 git commit 每轮一次（推荐勾，跨迭代回滚靠它）/ 安装项目内依赖 / 起本地服务跑验收。没勾 = 不允许。**永不项（push、对外发布、删项目外文件）不出现在选项里**——它们不是用户可以授权的 |

## 转成 AskUserQuestion 的规则

主会话拿到 PO 回传的题目后：

- 每次调用 ≤4 题（工具上限），题多分批：固定维度批在前，自出题批在后。
- 每题 2-4 个选项；**PO 的推荐项排第一，label 末尾加「（推荐）」**；description 一句话写清选它意味着什么——尤其范围题，要写明「不勾 = 划进非目标」。
- header ≤12 字符（「目标用户」「形态」「范围」「质量」「预算」「授权」）。
- 范围、授权用 `multiSelect: true`，其余单选。
- 用户永远可以选 Other 自由输入——**引导不是锁死**。Other 的原话和任何 notes 原样传回 PO，不要替用户翻译。
- 用户的答案暴露了新分叉（比如 Other 里提了选项外的平台）→ PO 可出下一批题，但**全流程最多两批**。

## 落定规则

- 每个答案由 PO 写进宪章对应条款并标出处「（问卷）」。
- 两批之后仍待定的按 PO 推荐落定、标「（默认）」——用户在最终确认草稿时看得见、改得了。
- **问卷不能代替最终确认**：草稿定稿后仍按 show-file 展示全文，用户点头才转正。问卷保证的是「草稿第一版就接近终稿、确认时只需扫一眼非目标和预算」，不是跳过确认。
