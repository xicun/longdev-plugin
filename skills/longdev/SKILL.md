# longdev

## 插件身份与协议路径

- 本 skill 的插件身份由宿主的 marketplace/plugin 清单决定。Codex 原生安装使用 `longdev@zzm-plugins`，技能命名空间通常为 `longdev:longdev`；不要把仓库目录名 `longdev-plugin` 推断成宿主命名空间。
- 当前文件的规范位置是 `<plugin-root>/skills/longdev/SKILL.md`，共享协议的规范位置是同一目录下的 `references/execution-protocol.md`。读取协议时以**实际加载的本文件所在目录**为基准解析相对链接；不要从 `<plugin-root>/<version>/` 或其它版本目录直接拼接 `references`。
- 主会话派发角色时优先传递解析后的协议绝对路径；角色说明中的 `skills/longdev/references/...` 仅表示插件根目录相对路径，不能替代主会话提供的绝对路径。

开工读取 `../../.claude-plugin/plugin.json`，报告 `longdev v<version>`。模型默认继承主会话；仅在用户或适用项目约定明确指定时覆盖，不根据猜测的价格或模型等级自动降级。

先读 [执行协议](references/execution-protocol.md)。它统一需求、状态、证据、基线与授权约定；autopilot 及所有 longdev 角色使用同一协议。需要跨客户端或跨会话继续时，再读 [会话运行时适配](references/session-runtime.md)。会话可替换，任务状态不能只存在于对话历史。

已知 compact/恢复/模型切换后先按会话适配重读规则与任务现场。每阶段和任务结束检查目标、队列、状态及证据一致性；需要 new 时先备好 `context/current.md` 与 `context/next-prompt.md`，记录换会话依据。没有可靠上下文指标时标未知，不猜百分比、不把技能当自动重启器。

收到异常/验收失败反馈时主动读取 [bug-reports](../bug-reports/SKILL.md)，先登记原始反馈及逐项去向，再修复。立项/续接读取相关问题摘要，派发关联 Bug 与反馈编号；修复后再次反馈升级调查。review/gate 与交付按执行协议的“开发反馈与项目问题档案”检查原始反馈覆盖和当前证据，交接保留编号及下一步；不用阶段记录复制问题事实。

启动时先判断用户意图：说“先预览迁移”“迁移 dry-run”“只看迁移情况”时，只执行下面命令加 `--dry-run`，不得先正式迁移；`status`/讨论只加 `--check`。已获授权的实施启动/续接才执行无只读参数的命令：

`python3 -B "<本 SKILL 所在目录>/scripts/migrate_workspace.py" --project "<当前项目绝对根目录>"`

Windows 使用可用 Python 3。脚本由实际安装包定位，仅盘点当前工作区 `.claude/longdev/`、`.claude/autopilot/`、带前导空格的 `.claude` 与 `.longdev` 候选，不扫描别的项目，不碰客户端配置/skills/runtime。根据内容和依赖保守分类，不能只靠目录或“已完成”迁走记录。`--dry-run` 输出每任务依据/分类、逐文件源/目标、迁移/历史归档/保留/去重/冲突及 Git 前提；不写目录、锁、journal、索引。`--check` 仅输出简短状态。

只读 exit 0=无待处理记录，1=存在可处理/待跟踪动作，2=需核对或受阻；正式执行 `awaiting_tracking` 以 exit 0 返回，表示复制已校验但旧入口尚未收掉。主会话可继续当前任务 review/gate 和限定提交，再重跑脚本完成逐文件保护归档，不能因等待 Git 跟踪而阻止使其满足的提交。`needs_review`/冲突保留原内容，报告具体项目及独立可继续范围，不宣称整体收敛。详细契约见 [执行协议](references/execution-protocol.md#持久记录与启动迁移)。

主会话在派发前运行 `scripts/task_path.py resolve --project "<项目绝对根>" --kind longdev --name "<任务名>"`，将返回的规范绝对路径作为唯一 `TASK_DIR`，同时传递 guard 脚本绝对路径。每次写任务记录/证据前先运行 `task_path.py check --project "<项目绝对根>" --task "<TASK_DIR>" --target "<实际写入绝对路径>"`；exit 0 后只写已检查目标。角色不得从 cwd 重拼路径。guard 拒绝相对、前导空格、旧根、越界、symlink/reparse 和保留名 `archive`；失败先修正入口，不绕过。它约束本插件角色流程，不能阻止任意旧客户端写文件；旧分叉由下次盘点发现。

## 组织与分工

每个任务使用 `docs/longdev/<kebab-case任务名>/`。PLAN 是精简索引，细节按需读取；不以硬行数限制删掉需求、证据或未解决问题。

| 路径 | 内容与写入者 |
|---|---|
| `PLAN.md` | 目标、授权、R/V 索引、阶段依赖及状态、全局决策；planner 建立，主会话维护检查/验收状态 |
| `stages/N.md` | planner 写阶段入口；implementer 追加执行、修复与交接记录 |
| `notes/`、`scout/` | 契约、研究和必要的长表；复用已有需求/设计事实源，无既有来源且获持久记录授权时才新建 `notes/analysis-design.md`，PLAN 只索引 |
| `evidence/` | 可携带的产物 manifest、验证摘要与限制；不能只存本机日志路径 |
| 项目 `.work/longdev/<任务>/baselines/`、`evidence/` | 本机起点补丁、副本、原始日志/图片；按项目规则忽略，不作为跨机器唯一证据 |
| `reviews/stage-N.md`、`reviews/final.md` | reviewer / final-reviewer 独立审查 |
| `gates/stage-N.md`、`gates/final.md` | 主会话记录验证覆盖、真实执行结果与通过依据 |
| `decisions/` | 重要决策的依据、授权、影响及后续验证 |

### 测试用例闭环（checks + testcases + checker）

- 项目级**共享测试用例库**在 `<项目>/testcases/`（schema 见 `skills/checks/references/catalog-schema.md`）；它是被开发项目的内容，所有任务共享并引用子集，不为任务复制用例。harness/插件各自是自己项目的一份库，不进使用方项目。
- `longdev-testcases` 角色维护库：Plan 阶段为对象设计/补全用例并把任务引用子集映射到 R/V；bug 修复验证通过且符合客观门槛（可复现、回归价值高、稳定）时晋升为回归 case。
- 需求分析采用 [requirements-design](../requirements-design/SKILL.md)，主会话可直接使用，按需委派 `longdev-requirements-designer`；角色复用需求/设计来源，获授权后才落文档，不改业务代码或 PLAN。planner 沿用稳定 R/V，补阶段和依赖映射。
- `longdev-checker` 角色执行验证：每阶段用 `check_runner.py --cases <子集>` 跑回归、出 manifest/指纹证据；收口跑全量闭环。checker 与 reviewer 职责不同且独立（checker 验行为/回归，reviewer 审设计/覆盖）。
- 运行器 `skills/checks/scripts/check_runner.py` 是通用机制；库由项目提供、用例来源是 testcases 角色按 Plan 构建，不把 harness/插件自身用例带进使用方项目。
角色定义只有一份：插件根目录 `agents/longdev-<角色>.md`。派发前读取对应角色正文，并传入项目、任务、协议、角色文件的绝对路径。Claude 使用已加载的 Agent/消息工具；Codex 使用实际可用的 sub-agent 工具；dsh 先检查 profile 暴露的独立 agent/session 工具。不能根据文件存在假定角色已注册，也不能凭客户端名称猜工具参数。缺少独立入口时可继续授权内实现和自检，但 review/final-review/acceptance 必须由未参与实现的独立会话或审查者执行；同一会话换角色不算独立审查，缺口保持待检查。独立调研可并发，共享文件实现串行。恢复后的旧 agent ID 不保证有效，必要时新建角色并从文件续接。

主会话负责目标、授权、状态、证据与跨角色衔接，默认收摘要和文件指针；为了判断阻碍、核实证据或保护用户改动，可以读必要正文、代码和原始日志。阅读先定位再展开，文件变化或证据不足时允许复读。禁止把摘要长度作为省略阻塞问题的理由。

### 工作流触发与主会话变更承接

- longdev 通常由上层 harness 路由：用户明确要求 longdev/分阶段开发/续接任务，或任务属于新功能、重构、迁移、跨模块改动、跨会话续接或需要独立检查时进入本技能。仅局部、可逆、单一路径的小改动不因文件数量或对话长度机械升级。技能被直接加载而未经过路由时，也按同一标准确认任务形态。
- 主会话是执行中的唯一变更入口。收到新的 vibe 或临时要求时，先在 PLAN 的变更队列或当前阶段的“入口变更记录”登记 `C01` 等编号，再分类为当前需求补充、当前范围扩展、独立任务或替换原目标；不得直接把未分类内容写进实现。
- 当前任务的变更要更新 R/V、阶段依赖和验收入口；影响已有实现、测试、配置或验收条件时，标记受影响的旧证据失效，并回到实施、checker、reviewer 和主会话 gate 的必要环节。独立事项进入队列或新任务；替换原目标时保留旧记录和用户依据。
- implementer 正在写共享文件时，主会话先登记并等待安全边界或结束当前写入，再重规划；不得让两个写入者并行修改同一任务记录或产物。用户指定主会话实现时仍遵守相同的记录、独立审查和 gate 要求。

使用有图片输入限制的 DeepSeek v4 私有化配置时，遵守执行协议的“受限模型的视觉处理与交接”：主会话纯文字，派发时明确图片处理入口和纯文字回传要求，不因客户端不同而忽略限制。视觉检查经文字转换或独立临时会话执行，不假定子 agent 自动隔离历史。

## A. 识别任务与立项

1. 完成上述启动迁移/只读探测后，用 Glob/文件列表检查新任务目录及 PLAN，读取候选状态、授权和剩余事项。`docs/` 是唯一权威入口，不静默重导入旧分叉；`archive/` 不作为活动任务枚举。用户明确指定任务或新目标时按其指示处理；只有多个候选且无法推断目标时才澄清，不覆盖已有任务。
2. 问答、讨论和 `status` 只读取并汇报。明确实施目标时建立任务目录和任务起点基线（见执行协议），按需派 scout 调研未知依赖。
3. 在 planner 前按需使用 [requirements-design](../requirements-design/SKILL.md) 或派 `longdev-requirements-designer`，提供目标原话、授权、既有 R/V、scout 和需求事实源指针；持久设计可参考 `references/analysis-design-template.md`。已有充分且可追溯的需求/设计时直接引用，不重编号或另建第二套内容。仅讨论/设计授权在目标达成后结束，不自动进入实施。
4. 读取分析设计产物并执行设计 gate：核对目标/范围/边界、需求-设计映射、可行性证据、兼容策略和真正待决定项；只有关键意图、重大取舍、外部影响或授权缺口才集中提问。阶段小结或章节完成不构成暂停，能独立推进的调查和设计继续进行。
5. 派 planner：给分析设计路径、用户要求原话、已有授权/决定、调研指针和 `references/plan-template.md`、`references/stage-template.md`。planner 消费稳定 R/设计映射，产出 `PLAN.draft.md` 与阶段入口；拆分依据是风险、耦合、依赖和可独立验证性。
6. 核对所有需求已纳入 R/V 映射。用户已授权方案且无关键缺口时，直接将草稿转为 PLAN 并推进，不固定重复确认；testcases 在设计稳定后维护用例并映射 R/V。
7. 展示计划链接及简短阶段摘要；需要辅助展示可读 `references/show-file.md`。记录授权来源与适用边界，不能用未回复替代批准。

调查与验证调用遵守执行协议的“调查收敛与工具异常”：调用前明确事实/验收项及预期信息，结果后把结论、有效证据、剩余和下一动作写入已有记录；纯问答不强制建档。相关产物与条件未变且已有有效证据时不重跑成功验证。无新依据重复或连续三次无新事实时形成收敛决定，优先交付/推进独立工作，不强制提问或阻塞。空 stdout、no output 按协议和退出码判断，有 ID 的 pending 按工具接口恢复；工具丢失/异常保留原始错误并限制重试，不当需求未完成，不自动切换用户选定模型，也不据此断言任何模型（包括 GLM）的能力。

## B. 续接

1. 读取 PLAN、当前阶段入口和相关 review/gate/证据摘要，检查磁盘实际产物及适用授权。不能仅凭 `✅`、阶段表或“已完成”跳过检查。
   明确当前选定任务及启动/续接授权，完成上述 resolve 且旧写入者已停止后，自动调用 `python3 -B "<本 SKILL 所在目录>/scripts/compatibility_upgrade.py" --project "<项目绝对根>" --task "docs/longdev/<任务名>"`。`--task` 必须是解析后的 TASK_DIR 相对项目根的规范路径，不传绝对路径；该独立入口只处理当前任务，不用仍会盘点全工作区的 `migrate_workspace.py --task` 代替。纯讨论、状态查询只加 `--check`，明确预览加 `--dry-run`；不能因旧任务存在就自动续接。终态不重开；旁车仅保留快照、不改需求/授权/状态或自动采用新流程。冲突/未知结果保留现场并报告受影响范围；缺 PLAN 的新任务先建立已授权记录，不能用占位内容凑升级成功。
2. 从最早尚未满足依赖或缺少有效证据的环节继续：已实现但缺 review/gate → 待检查；相关文件变化 → 受影响的旧证据过期；外部条件缺失 → 受阻并继续独立工作。旧版状态保留为历史声明，补核证据后再映射到新状态。旧任务只在需求讨论、阶段切换或恢复等安全交接点按需接入分析设计；已有内容足够时直接复用，不修改历史语义或强制倒退阶段。
3. 信息缺失时针对性读取/调研；无需重做已有且仍有效的调查。简短说明实际进度和本次入口，进入 C。
4. **跨会话恢复**：如果当前会话需要结束或更换客户端，先写 `context/current.md` 并校验交接包，再停止旧会话。新会话先读交接包和实际现场；不得把 `resume`、`fork` 或客户端退出码当作阶段通过。

## C. 推进阶段

1. **准备**：确认分析设计（新任务）或既有需求/设计输入（旧任务）已可追溯，依赖已检查通过、关键歧义已解决，记录阶段起点基线。将阶段置为执行中，派 implementer，给阶段号、基线路径和相关决策。保护既有改动，不用 Git 恢复或清理工作区来制造干净基线。
2. **实现**：implementer 完成当前阶段、自检并记录证据，只能将状态更新为待检查；不能把下一阶段设为执行中，也不能写检查通过或已验收。随后派 `checker` 用 `check_runner.py --cases <本阶段引用子集>` 跑回归、出 manifest/指纹证据（不依赖实现者自测）。前置条件不符、证据不足或范围变化需记录影响，由主会话处理；尺寸增大先重新评估拆分，无须机械等用户。
3. **独立审查**：派 reviewer，给阶段入口、基线、当前产物状态和报告路径。它先按要求形成自己的检查结果，再对照实现者记录；检查需求覆盖、代码正确性、行为验证（核对 checker 证据）、授权边界及记录属实性。
4. **处理问题与决策**：阻塞项交回 implementer 修复，再由 reviewer 复查受影响范围。常规授权内技术取舍直接记录；复杂分叉可派 decider。超授权的目标/范围/验收或重要取舍须用户决定，已授权决定不重复请求。累计决策数量不触发机械停机。任何决策引起的代码、配置或行为变更都返回本步骤修复/审查，再进入 gate，绝不直接跳到下一阶段。
5. **主会话 gate**：读取预期 V ID 全集及其方法；核实实际改动范围（含未跟踪文件）、review 结论、证据完整性及产物指纹；亲自执行阶段必需验收操作，保留原始日志与真实结果。受限模型的视觉操作按共享协议通过隔离入口执行，主会话核验文字证据，不为 gate 重新载入图片；最终 gate 同样适用。命令成功只证明该命令的结果，不能替代需求覆盖。测试 skip/空断言等搜索命中需结合上下文审查，不因字符串命中自动判失败。
6. **落盘与阶段提交**：仅在全部必需 V 有当前有效证据、review 无阻塞且 gate 通过后，由主会话同步检查通过状态、review/gate 和交接记录，然后按共享协议“阶段本地提交”自动提交本阶段归属明确的代码及持久记录。不得把多个已通过阶段积压到最后；提交失败/改动无法安全分离时记录提交受阻并先解决，不静默启动下一阶段。用户明确禁止提交、无 Git、确实无变化按协议记录对应结果。提交成功后简报 commit、证据和剩余事项，继续已授权且依赖满足的下一阶段。检查通过、Git 提交和用户验收分别记录。
7. **失败处理**：按共享协议区分产品缺陷、运行时/适配器异常和正常无输出/异步等待，保留原始结果。无新证据、修复或暂态依据不重试；同动作有依据也至多重试一次，再失败即重新评估入口和依赖、记录下一步并推进独立工作。工具异常不是需求缺口，不自动授权切换模型/客户端。只有具体必要条件缺失才受阻、只有关键用户信息缺失才提问。decider 不可用时主会话仍可处理已授权常规判断，如实记录角色缺口。

## D. 收尾与验收

1. 所有阶段检查通过后先派 `checker` 运行任务引用的**全量**闭环用例，核对所有 R/V 对应 case 通过并出证据；再派 final-reviewer，核对原始需求全集、跨阶段接缝、决策传播、遗留事项与端到端目标，执行计划要求的全量验证。以前的阶段测试绿不能代替整体检查。
   autopilot 存在隔离项时可按其协议对明确的独立交付子集做整体审查，同时报告全量 R/V 缺口。此为部分交付检查，不满足整任务通过条件；受阻时允许形成失败报告，不必伪造所有阶段通过才能报告。
2. 发现阻塞则派 implementer 做有边界收尾修复，明确关联 R/V 和阶段；修复后重新进行受影响阶段审查、整体审查及 gate。主会话执行最终必需验证，写 `gates/final.md`；相同产物上已有的有效阶段结果无需无理由重跑。
3. 整体检查通过后将任务置为待验收；新增的最终 review/gate、修复和交接记录同样按阶段提交规则形成收尾提交，不能遗留未提交的关键状态。交付成果链接、commit、覆盖情况、验证证据与限制。只有用户明确接受，或有效自动验收授权下由指定 acceptance 角色按标准通过，才能写已验收。授权的发布等后续任务继续办理；未授权外部操作在可审阅结果就绪后申请批准。

## E. 特殊情况

- 用户指定主会话实现时可直接执行，同样保持独立 reviewer 与 gate；无需因参与实现强制清空上下文。
- 旧版单文件计划默认原位复用，以兼容旁车保留快照；不因升级另建或重写 PLAN。确有结构调整需要且已授权时才保存保护副本（如 `PLAN.legacy.md`）并抽取索引，沿用原 R/V、用户决定和历史状态，不把历史完成声明重新解释为已验收，也不为了迁移修改业务代码。缺基线或验证证据如实记录，仅补核受影响的后续工作。
- 新版分析设计能力对旧任务采取渐进兼容：旧记录已有等价内容时以其为输入并保留原路径/语义；仅在安全交接点补建 `analysis-design.md` 索引或缺口，不自动改变 R/V、授权、状态或历史证据。无法识别格式时保留原件、报告受阻，禁止盲目转换。
- 新增行为按风险补充必要行为测试；低风险文档、配置和可逆改动可采用匹配的检查。不能为减少测试成本取消既定验收，也不写仅复制实现的测试。
- 所有角色的输出是需核实的工作记录，主会话工具输出也有覆盖边界；不宣称某一角色或工具天然不可伪造。统计差异先核对产物、环境、命令和测试选择，再判断原因。
