# PLAN.md 模板

planner 立项时按此结构写 `.claude/longdev/PLAN.draft.md`，用户确认后由主会话改名为 `PLAN.md`。写给「一个没有任何本次会话 context 的人」看。

```markdown
# <任务名>

**目标**：<一到三句话说明做完之后什么变了。写可观察的结果，不要写"优化""改进"这类空词。收尾审查会拿这一句端到端验。>

**创建于**：<YYYY-MM-DD>　**最后更新**：<YYYY-MM-DD>
**基线 commit**：<立项时 `git rev-parse HEAD` 的输出；非 git 仓库写"无"。收尾审查用它算整个任务的全量 diff。>

## 阶段

- [x] 1. <阶段目标> —— 完成于 <日期>
- [ ] 2. <阶段目标>　← 当前
- [ ] 3. <阶段目标>【主会话】
- [ ] 4. <阶段目标>

<!-- 【主会话】= 该阶段需要用户现场决策，由主会话亲自执行（SKILL.md 的 D 流程）；其余阶段默认派给 longdev-implementer。 -->

## 关键文件

| 路径 | 作用 |
|---|---|
| `src/a/b.ts:120` | <一句话> |
| `src/c/d.ts` | <一句话> |

## 调研结论

<只写影响方案的结论，每条一两句、注明出处文件:行号，并指向完整报告：`.claude/longdev/scout/<主题>.md`。不要把 scout 报告抄进来。>

## 已做出的决策

- **<决策点>**（立项）：选了 <方案>，因为 <原因>。放弃了 <备选> 因为 <原因>。
- **<决策点>**（阶段 N 追加）：...

<!-- 每条标注是立项定的还是哪个阶段追加的——收尾审查靠这个查"后期改了决策、早期代码没回头改"。 -->

## 踩过的坑

- <现象> → 原因是 <...>，处理方式 <...>

## 下一阶段入口

**阶段 N：<目标>**

- 要改的文件：`...`、`...`
- 前置条件：<已经满足了什么>
- 完成标准：<跑什么命令看到什么结果——优先是测试。要新增的测试点名写出：测什么行为、放哪个文件>
- 已知风险：<...>

## 验证方式

**运行命令**：<本项目怎么跑测试/构建。写确切命令：单个文件/包怎么跑，全量怎么跑。>

**测试约定**：<框架、测试文件位置和命名、mock 惯例。新增行为的阶段必须随实现补单元测试。项目没有测试基础设施的，这里写"不引入，验证靠 <什么>"，并在「已做出的决策」里记下这条是立项时和用户定的。>
```

## 填写纪律

- 这个文件是每个 implementer 的**唯一输入**：「下一阶段入口」写得不够一个陌生人开工，那个阶段就会失败或跑偏。立项时就按这个标准写第 1 阶段入口。
- 编排模式下，各阶段的勾选、决策、坑、下一阶段入口由该阶段的 implementer 更新；主会话只 `grep` 阶段清单抽查勾选状态，内容是否属实由 reviewer 核。
- **决策**和**坑**这两节是这个文件最值钱的部分。它们是无法从代码里读回来的信息——代码只能告诉你现在是什么样，不能告诉你为什么不是另一样。
- 「调研结论」只放结论和指针。scout 的完整报告在 `.claude/longdev/scout/`，需要细节的 agent 自己去读——PLAN.md 越长，每个 implementer 开工时读的越多。
- 每个阶段收尾都要更新「最后更新」和「下一阶段入口」。
- 相对日期一律换成绝对日期。
- 阶段全部完成、收尾审查通过后，在标题下加一行 `**状态：已完成**`，文件保留作为决策记录。`.claude/longdev/reviews/` 和 `scout/` 一并保留。
