# PLAN.md 模板

创建 `.claude/longdev/PLAN.md` 时按此结构填写。写给「一个没有任何本次会话 context 的人」看。

```markdown
# <任务名>

**目标**：<一到三句话说明做完之后什么变了。写可观察的结果，不要写"优化""改进"这类空词。>

**创建于**：<YYYY-MM-DD>　**最后更新**：<YYYY-MM-DD>

## 阶段

- [x] 1. <阶段目标> —— 完成于 <日期>
- [ ] 2. <阶段目标>　← 当前
- [ ] 3. <阶段目标>【主会话】
- [ ] 4. <阶段目标>

<!-- 【主会话】= 该阶段需要用户现场决策，由主会话亲自执行（SKILL.md 的 D 流程）；其余阶段默认派给 longdev-implementer。 -->

## 关键文件

| 路径 | 作用 |
|---|---|
| `src/a/b.ts:120` | <一句话> |
| `src/c/d.ts` | <一句话> |

## 调研结论

<scout 查到的、影响方案的事实。只写事实，不写猜测。每条注明出处文件:行号。>

## 已做出的决策

- **<决策点>**：选了 <方案>，因为 <原因>。放弃了 <备选> 因为 <原因>。
- ...

## 踩过的坑

- <现象> → 原因是 <...>，处理方式 <...>

## 下一阶段入口

**阶段 N：<目标>**

- 要改的文件：`...`、`...`
- 前置条件：<已经满足了什么>
- 完成标准：<跑什么命令看到什么结果，或观察到什么行为>
- 已知风险：<...>

## 验证方式

<本项目怎么跑测试/构建。写确切命令。>
```

## 填写纪律

- 这个文件是每个 implementer 的**唯一输入**：「下一阶段入口」写得不够一个陌生人开工，那个阶段就会失败或跑偏。立项时就按这个标准写第 1 阶段入口。
- 编排模式下，各阶段的勾选、决策、坑、下一阶段入口由该阶段的 implementer 更新；主会话只抽查。
- **决策**和**坑**这两节是这个文件最值钱的部分。它们是无法从代码里读回来的信息——代码只能告诉你现在是什么样，不能告诉你为什么不是另一样。
- 每个阶段收尾都要更新「最后更新」和「下一阶段入口」。
- 相对日期一律换成绝对日期。
- 阶段全部完成后，在标题下加一行 `**状态：已完成**`，文件保留作为决策记录。
