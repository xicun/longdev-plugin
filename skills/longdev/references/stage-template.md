# stages/N.md 模板

每个阶段一份，路径 `<任务目录>/stages/<N>.md`。两段：

- **入口**：planner 立项时写全部阶段的入口（后面阶段可以粗一些）；上一阶段的 implementer 收尾时精修下一阶段的入口。
- **完成记录**：本阶段 implementer 收尾时追加。

**硬上限 80 行。** 读者是一个只读 `PLAN.md` + 本文件 + 上一阶段「交接」的陌生人——写给他看，绝不写"见上文""如前所述"。

```markdown
# 阶段 N：<目标>

## 入口

**完成标准**
<跑什么命令看到什么结果。优先是测试——点名要新增的测试：测什么行为、放哪个文件。>

**要改的文件**
- `path/a.ts` — <改什么>
- `path/b.ts` — <改什么>

<!-- 超过 8 个文件或预计 >400 行改动，说明这个阶段该拆成两个。planner 立项时就要守住；
     implementer 开工发现超了，先上报，不要闷头做完。 -->

**前置条件**
<上一阶段已经做出了什么、现在代码里已经有什么。写事实，不写"阶段 N-1 做完了"。>

**相关参考**
- `notes/<主题>.md` — <为什么本阶段要看它>
- 没有就写"无"

**已知风险**
<可能踩的地方，或需要特别小心的兼容性。没有就写"无"。>

## 完成记录

<!-- 本阶段 implementer 收尾时追加。上面「入口」一节保持原样不要改——
     收尾审查会比对入口的完成标准和这里的实际结果。 -->

**完成于**：<YYYY-MM-DD>

**实际改动**
- `file:line` — <一句话>

**测试**
<新增/修改了哪些测试文件、覆盖什么行为。没加就写为什么。>

**本阶段决策**
- **<决策点>**：选了 <方案>，因为 <原因>。
<!-- 只影响本阶段的写这里。判断后面阶段也会用到的，同时提升到 PLAN.md「全局决策」并标（阶段 N 提升）。 -->

**本阶段坑**
- <现象> → 原因 <...>，处理 <...>
<!-- 任何后续阶段都可能再踩的，提升到 PLAN.md「全局坑」。 -->

**验证输出**
<跑了什么命令、真实输出摘要。失败过就写失败过、怎么修的。>

**给下一阶段的交接**
<下一阶段的 implementer 只会读这一小节 + PLAN.md + 它自己的 stages/N+1.md。
 所以把"我做完之后现场变成什么样了、有什么是它必须知道的"写在这里。没有就写"无"。>
```

## 纪律

- 「入口」写完就冻结，`完成记录` 只追加。收尾审查靠比对这两段判断阶段是否达成目标。
- 修复轮不改这份文件的结构，把修了什么补进「验证输出」。
- 本阶段的文件清单、决策、坑都留在这里——**不要往 PLAN.md 搬**，除非确实跨阶段。
